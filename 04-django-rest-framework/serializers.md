### DRF-SER-001: What is a Serializer in DRF and how does it work?

**Difficulty:** Basic  
**Topic:** DRF Fundamentals

#### 1. Simple Explanation
In web development, a database works with complex Python objects and database rows, while web browsers and mobile apps understand text format called **JSON**.  
A **Serializer** is a two-way translator:
1. It translates complex Python database models into clean JSON to send to clients (**Serialization / Reading**).
2. It takes incoming JSON from clients, checks if the data is valid, and converts it into Python objects to save into the database (**Deserialization / Writing**).

#### 2. Easy Real-World Example
Imagine a currency exchange counter at an airport:
- When you land in India with US Dollars, the counter validates that your dollars are genuine (Validation) and converts them into Indian Rupees for you to spend (Deserialization).
- When you leave, the counter converts your Rupees back into international currency for the rest of the world to accept (Serialization).

#### 3. One-Line Interview Answer
A **DRF Serializer** is a component that controls the conversion between complex Python model instances and primitive datatypes (JSON/XML), while enforcing strict request validation and object persistence rules.

#### 4. Serializer vs ModelSerializer Comparison

| Feature | `serializers.Serializer` | `serializers.ModelSerializer` |
| :--- | :--- | :--- |
| **Boilerplate** | High: Every field must be explicitly declared | Low: Automatically inspects Django Model fields |
| **Validation** | Custom field validators | Automatically creates validators from model constraints (`unique`, `max_length`, `null=False`) |
| **Default `create()`/`update()`**| Must be manually implemented | Automatically generated by DRF |
| **Best Used For** | Non-model data (login endpoints, external API proxies, OTP verification) | Standard database CRUD APIs |

#### 5. Practical Implementation Example

```python
from rest_framework import serializers
from django.contrib.auth.models import User

class UserRegistrationSerializer(serializers.ModelSerializer):
    password = serializers.CharField(write_only=True, min_length=8)
    confirm_password = serializers.CharField(write_only=True)
    full_name = serializers.SerializerMethodField()

    class Meta:
        model = User
        fields = ['id', 'username', 'email', 'password', 'confirm_password', 'full_name']

    def get_full_name(self, obj: User) -> str:
        """Computed dynamic field (SerializerMethodField is read-only)"""
        return f"{obj.first_name} {obj.last_name}".strip() or obj.username

    def validate_email(self, value: str) -> str:
        """Field-level validator for 'email'"""
        if not value.endswith(("@gmail.com", "@company.com")):
            raise serializers.ValidationError("Only Gmail or corporate company domains are allowed.")
        return value.lower()

    def validate(self, attrs: dict) -> dict:
        """Object-level validator (cross-field comparison)"""
        if attrs.get("password") != attrs.get("confirm_password"):
            raise serializers.ValidationError({"confirm_password": "Passwords do not match."})
        return attrs

    def create(self, validated_data: dict) -> User:
        """Custom creation logic (excluding confirm_password)"""
        validated_data.pop("confirm_password")
        return User.objects.create_user(**validated_data)
```

#### 6. Code Explanation
- `write_only=True`: Ensures the password is accepted in incoming requests but **never returned in outgoing API JSON responses** (security requirement).
- `SerializerMethodField()`: Generates a calculated read-only value by executing `get_<field_name>()`.
- `validate_email(self, value)`: Field-level validation hook.
- `validate(self, attrs)`: Cross-field validation hook for comparing two fields together.

### DRF-SER-002: How do you eliminate N+1 queries in Nested Serializers?

**Difficulty:** Advanced  
**Topic:** DRF Performance Optimization

#### The Problem:
When serializing an author who has 50 books:
```python
class BookSerializer(serializers.ModelSerializer):
    class Meta:
        model = Book
        fields = ['id', 'title']

class AuthorSerializer(serializers.ModelSerializer):
    books = BookSerializer(many=True, read_only=True) # Nested serializer!
    class Meta:
        model = Author
        fields = ['id', 'name', 'books']
```
If your View executes:
```python
authors = Author.objects.all() # 1 Query
serializer = AuthorSerializer(authors, many=True)
return Response(serializer.data)
```
For every author, DRF executes a separate SQL query to fetch their books, triggering the **N+1 query explosion**!

#### The Solution:
Always preload nested relationships in the view's QuerySet using **`prefetch_related`** or **`select_related`**:
```python
# In your View / ViewSet:
def get_queryset(self):
    return Author.objects.prefetch_related('books').all() # Drops from 101 queries to exactly 2 queries!
```
